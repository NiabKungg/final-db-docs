จุดประสงค์

เคลียร์โครงสร้างเดิมออกให้หมดก่อนสร้างใหม่ — ตามเงื่อนไขอาจารย์ที่ให้ "DROP ทุกตารางแล้วสร้างใหม่ Face-to-face" เพื่อพิสูจน์ว่าสคริปต์ทั้งชุดทำงานได้ตั้งแต่ศูนย์จริง ๆ ไม่ได้พึ่งของเก่า

อธิบายการทำงานทีละจุด

  • ลำดับการ DROP สำคัญมาก — ต้องลบ "ตารางลูก" (มี FK อ้างอิง) ก่อน "ตารางแม่" เสมอ ลำดับในไฟล์เรียงจากปลายทางสุดของสาย FK ย้อนกลับมา: LOG → RECEIPT_RECORD → DOCUMENT_DETAIL → DOCUMENT → EMPLOYEE → ADMIN → DEPARTMENT_HEAD → DEPARTMENT
  • CASCADE CONSTRAINTS — สั่งให้ Oracle ลบ constraint (FK) ที่ตารางอื่นชี้เข้ามาทิ้งไปด้วย ถ้าไม่ใส่แล้วมีตารางลูกค้างอยู่ จะเกิด ORA-02266 (cannot drop table ... referenced by a foreign key)
  • ถ้าตารางยังไม่มีอยู่เลย จะได้ ORA-00942 (table or view does not exist) — ไม่ใช่ปัญหา แปลว่าไม่มีอะไรให้ลบ ข้ามต่อได้ (ตอน deploy จริงวันนี้ BA ไม่มีตารางให้ลบ จึงข้ามขั้นนี้ไป)
จุดซักถาม: ทำไมไม่ใช้ DROP TABLE ... PURGE? — ปกติ DROP ยังเหลือ object ใน recyclebin แต่เพราะเราจะสร้างตารางชื่อเดิมขึ้นมาใหม่ทันที ชื่อซ้ำกับ recyclebin ไม่กระทบการ CREATE และ Script ตรวจสอบของอาจารย์ (USER_TABLES) ไม่แสดง recyclebin อยู่แล้ว

จุดประสงค์

แปลง ER Diagram (Chen Notation 8 เอนทิตี) เป็นโครงสร้างตารางจริงบน Oracle พร้อม PK, FK, NOT NULL ครบทุกความสัมพันธ์

อธิบายการทำงานทีละตาราง

  1. Department (แผนก) — สร้างก่อนสุดเพราะเป็น "แม่" ที่ทุกตารางคนอื่นชี้มา มีคอลัมน์ head_code ไว้เก็บหัวหน้าแผนก แต่ยังไม่ผูก FK ตอน CREATE — เพราะ DEPARTMENT_HEAD ยังไม่ถูกสร้าง (ต่างฝ่ายต่างอ้างถึงกันแบบวงจร 1:1)
  2. Department_Head (หัวหน้าแผนก) — มี FK fk_dh_dept ชี้กลับไป Department ได้เพราะ Department ถูกสร้างไปแล้ว
  3. ALTER TABLE (คำสั่งที่ 1.3) — ปิดวงจร 1:1 ด้วยการเติม FK fk_dept_head (head_code → DEPARTMENT_HEAD) ทีหลัง — นี่คือคำตอบของปัญหา circular reference: สร้างแม่ก่อน แล้วค่อยเติมสายสัมพันธ์ย้อนกลับ
  4. Admin (ธุรการ) และ Employee (พนักงาน) — โครงสร้างเหมือนกัน (code, name, position, branch, phone, dept_code) ต่างกันที่บทบาท: ธุรการ = คนร่าง/ส่งเอกสาร, พนักงาน = ปลายทางผู้รับทราบ
  5. Document (เอกสารหลัก) — รวม 2 ความสัมพันธ์จาก ER เป็น FK: created_by → ADMIN (ความสัมพันธ์ "ร่าง" 1:M) และ approved_by → DEPARTMENT_HEAD (ความสัมพันธ์ "อนุมัติ" 1:M)
  6. Document_Detail (รายละเอียดเอกสาร) — จาก Weak Entity ใน ER (สี่เหลี่ยมสองชั้น + Identifying Relationship) เก็บสาระสำคัญของระบบไว้ที่นี่: sla_limit (เกณฑ์เวลา), expire_date (กำหนดเส้นตาย), status (รอยืนยัน/อนุมัติแล้ว/ไม่อนุมัติ/กำลังดำเนินการ/ปิดงานแล้ว)
  7. Receipt_Record (บันทึกรับทราบ) — Transaction table เก็บหลักฐานการกดรับทราบ: IP (VARCHAR2(45) กว้างพอสำหรับ IPv6), เวลา TIMESTAMP และ FK สองเส้น (เอกสาร + พนักงาน)
  8. Log (ประวัติแจ้งเตือน) — เก็บว่าใครถูกแจ้งเรื่องอะไร ช่องทางไหน เมื่อไร — คอลัมน์ log_type ทำหน้าที่แทน Multivalued Attribute "ช่องทางที่ส่ง" ใน ER ด้วยหลัก 1NF: 1 แถวต่อ 1 ช่องทาง (จึงเห็นเอกสารเดียวมี LOG หลายแถวหลายช่องทาง)
จุดซักถาม: เบอร์โทร/สาขาใน ER เป็น Multivalued (วงรีสองชั้น) ทำไมเก็บคอลัมน์เดียว? — เลือกเก็บเบอร์หลักเบอร์เดียวเพื่อความเรียบง่ายของ dataset ถ้าต้องแก้ให้ตรงหลัก 1NF หน้างาน: แตกเป็นตารางย่อย เช่น EMPLOYEE_PHONE(code, phone) PK composite แล้วลบคอลัมน์เดิม

-- 1.1 ตาราง Department (แผนก)

    dept_code VARCHAR2(10),
    CONSTRAINT fk_admin_dept FOREIGN KEY (dept_code) REFERENCES Department(dept_code)

-- 1.5 ตาราง Employee (พนักงานในองค์กร)
CREATE TABLE Employee (
    code VARCHAR2(10) PRIMARY KEY,

    position VARCHAR2(100),
    branch VARCHAR2(100),
    dept_code VARCHAR2(10),
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_code) REFERENCES Department(dept_code)

    PRIMARY KEY (dept_code, phone),
    CONSTRAINT fk_dp_dept FOREIGN KEY (dept_code) REFERENCES Department(dept_code)

-- 1.5.2 ตารางย่อยเบอร์โทรหัวหน้าแผนก
CREATE TABLE Head_Phones (
    head_code VARCHAR2(10),
    phone     VARCHAR2(20),
    PRIMARY KEY (head_code, phone),
    CONSTRAINT fk_hp_head FOREIGN KEY (head_code) REFERENCES Department_Head(code)
);

-- 1.5.3 ตารางย่อยเบอร์โทรธุรการ
CREATE TABLE Admin_Phones (
    admin_code VARCHAR2(10),
    phone      VARCHAR2(20),
    PRIMARY KEY (admin_code, phone),
    CONSTRAINT fk_ap_admin FOREIGN KEY (admin_code) REFERENCES Admin(code)
);

-- 1.5.4 ตารางย่อยเบอร์โทรพนักงาน
CREATE TABLE Emp_Phones (
    emp_code VARCHAR2(10),
    phone    VARCHAR2(20),
    PRIMARY KEY (emp_code, phone),
    CONSTRAINT fk_ep_emp FOREIGN KEY (emp_code) REFERENCES Employee(code)
);

-- 1.6 ตาราง Document (เอกสารหลัก)
CREATE TABLE Document (
    doc_code VARCHAR2(20) PRIMARY KEY,
    title VARCHAR2(255) NOT NULL,
    approved_by VARCHAR2(10),
    created_by VARCHAR2(10),
    CONSTRAINT fk_doc_approved FOREIGN KEY (approved_by) REFERENCES Department_Head(code),
    CONSTRAINT fk_doc_created FOREIGN KEY (created_by) REFERENCES Admin(code)
);

-- 1.7 ตาราง Document_Detail (รายละเอียดเอกสาร)
CREATE TABLE Document_Detail (
    code VARCHAR2(10) PRIMARY KEY,
    doc_code VARCHAR2(20) NOT NULL,
    subject VARCHAR2(255),
    priority VARCHAR2(50),
    target_group VARCHAR2(100),
    sender_code VARCHAR2(10),
    doc_date DATE,
    expire_date DATE,
    sla_limit VARCHAR2(20),
    month VARCHAR2(20),
    status VARCHAR2(50),
    CONSTRAINT fk_dd_doc FOREIGN KEY (doc_code) REFERENCES Document(doc_code),
    CONSTRAINT fk_dd_sender FOREIGN KEY (sender_code) REFERENCES Admin(code)
);

-- 1.8 ตาราง Receipt_Record (บันทึกรับปลายทาง)
CREATE TABLE Receipt_Record (
    code VARCHAR2(10) PRIMARY KEY,
    ip_address VARCHAR2(45),
    sla_limit VARCHAR2(20),
    recipient_type VARCHAR2(100),
    received_datetime TIMESTAMP,
    detail_code VARCHAR2(10),
    confirmed_by VARCHAR2(10),
    CONSTRAINT fk_rec_detail FOREIGN KEY (detail_code) REFERENCES Document_Detail(code),
    CONSTRAINT fk_rec_emp FOREIGN KEY (confirmed_by) REFERENCES Employee(code)
);

-- 1.9 ตาราง Log (ประวัติการแจ้งเตือนและระบบ)
CREATE TABLE Log (
    code VARCHAR2(10) PRIMARY KEY,
    log_type VARCHAR2(50),
    message_sent VARCHAR2(255),
    notification_message VARCHAR2(4000),
    sent_datetime TIMESTAMP,
    emp_code VARCHAR2(10),
    detail_code VARCHAR2(10),
    CONSTRAINT fk_log_emp FOREIGN KEY (emp_code) REFERENCES Employee(code),
    CONSTRAINT fk_log_detail FOREIGN KEY (detail_code) REFERENCES Document_Detail(code)
);

จุดประสงค์

เติมข้อมูลจำลองที่สอดคล้องกันทั้ง 8 ตาราง (รวม 135 แถว) เพื่อให้รายงาน JOIN และการทดสอบ Procedure มีข้อมูลจริงให้ประมวลผล — ความสอดคล้อง (FK integrity) ตรวจแล้วทุกแถว ไม่มี reference แขวนลอย

โครงสร้างไฟล์ (เรียง 9 ส่วนตามลำดับ FK)

2.1 Department (8)→ 2.2 Department_Head (8)→ 2.3 UPDATE head_code (8)→ 2.4 Admin (10)→ 2.5 Employee (20)→ 2.6 Document (15)→ 2.7 Document_Detail (21)→ 2.8 Receipt_Record (21)→ 2.9 Log (32)→ COMMIT

อธิบายการทำงานทีละจุด

  • ส่วน 2.1 + 2.2 + 2.3 เป็นสามีชิ้นของวงจร 1:1 — INSERT แผนกด้วย head_code = NULL ก่อน (เพราะหัวหน้ายังไม่มีข้อมูล ผูก FK ไม่ได้) → INSERT หัวหน้าแผนกทั้ง 8 คน → แล้วค่อย UPDATE Department SET head_code = 'DH-xxx' ย้อนกลับ เป็นเทคนิคมาตรฐานแก้ปัญหาข้อมูลวนกันเอง
  • ลำดับ INSERT = ลำดับ FK เสมอ — พนักงานต้องมาก่อน Receipt_Record, Document ต้องมาก่อน Document_Detail ฯลฯ ถ้าสลับจะเจอ ORA-02291 (parent key not found) ทันที
  • วันที่ใช้ TO_DATE + format mask — เช่น TO_DATE('2026-08-07','YYYY-MM-DD') ป้องกันปัญหา NLS_DATE_FORMAT ต่างเครื่อง และเวลาใช้ TO_TIMESTAMP(...'YYYY-MM-DD HH24:MI:SS')
  • ข้อมูลถูกออกแบบให้ "มีเรื่องราว" — เอกสาร 15 ฉบับกระจายทุกแผนก, DD-004 ตั้งใจให้สถานะ "รอยืนยัน" เพื่อเป็นตัวชูโรงของไฟล์ทดสอบ (ขั้นที่ 5), LOG 32 แถวครอบคลุม 4 ช่องทาง (System Alert / SMS Warning / Email Notification / Mobile Push)
  • COMMIT ท้ายไฟล์ — ยืนยันทุกอย่างใน transaction เดียว ถ้ากลางทางพังทั้งชุดจะไม่ค้างเศษข้อมูล
ข้อควรระวัง: ไฟล์นี้ใหญ่ ~52KB — ตอนวางใน iSQL*Plus ให้วางทั้งไฟล์ในครั้งเดียวได้ แต่ถ้าเครื่องช้า/ตัดหาย ให้แบ่งรันเป็น 3 ส่วนตามหัวข้อ 2.1–2.5 / 2.6–2.7 / 2.8–2.9 ได้ (วันนี้ deploy จริงแบ่ง 3 ส่วนและผ่านทุกส่วน)
จุดซักถาม: ทำไม DD-004 ถึงตั้งสถานะ "รอยืนยัน" ไว้? — เพื่อใช้พิสูจน์ Transaction Processing ในขั้นที่ 5: เอกสารจะถูกอนุมัติและระบบสร้าง Log ให้เอง ผลก่อน-หลังเทียบได้ชัดต่อหน้าอาจารย์

จุดประสงค์

ครอบคลุมโจทย์ข้อ 3 ของอาจารย์: "เขียน Stored Procedure (PL/SQL) ตามโจทย์หลักของระบบงาน (Transaction Processing)" — ในระบบนี้ ทุกครั้งที่สถานะเอกสารเปลี่ยน ระบบต้องบันทึกประวัติการแจ้งเตือนให้พนักงานอัตโนมัติ และประวัตินี้ห้ามหายแม้งานหลักจะล้มเหลว

อธิบายการทำงานทีละบล็อก

  1. พารามิเตอร์ — รับ 5 ค่าเข้า (ประเภทแจ้งเตือน, ข้อความสรุป, ข้อความเต็ม, พนักงานปลายทาง, รายละเอียดเอกสาร) และส่ง 1 ค่าออก (o_log_code = รหัส Log ที่ระบบสร้างให้เอง เพื่อให้ผู้เรียกรู้ว่าบันทึกเป็นรหัสอะไร)
  2. PRAGMA AUTONOMOUS_TRANSACTION — หัวใจของ Procedure นี้: ประกาศว่า transaction ภายใน Procedure เป็นอิสระจาก transaction หลักที่เรียกมัน เมื่อ Procedure ทำ COMMIT ข้อมูล Log ถูกยืนยันถาวรทันที โดยไม่กระทบ (หรือถูกกระทบจาก) COMMIT/ROLLBACK ของงานหลัก — เหตุผลธุรกิจ: Log คือ audit trail ถ้างานหลัก rollback ก็ต้องมีบันทึกว่า "พยายามแล้วพังตรงไหน" ห้ามลบประวัติ
  3. บล็อกสร้างรหัสอัตโนมัติ — SELECT NVL(MAX(TO_NUMBER(SUBSTR(code,5))),0)+1 INTO v_next_num FROM Log WHERE REGEXP_LIKE(code,'^LOG-[0-9]+$') แปลว่า: มองเฉพาะแถวที่รหัสเป็นรูปแบบ LOG-ตัวเลข (กันแถวขยะรูปแบบอื่น), ดึงเลขท้ายออกมาด้วย SUBSTR ตำแหน่งที่ 5, หาค่ามากสุด +1 — ถ้าตารางว่างเปล่า NVL ครอบไว้ให้เริ่มที่ LOG-001 จากนั้น LPAD(...,3,'0') ขยายเลขให้ครบ 3 หลักเสมอ (LOG-001, LOG-033, LOG-100)
  4. INSERT + SYSTIMESTAMP — บันทึกแถวใหม่โดยเวลาใช้เวลา server จริง (ไม่ใช่เวลาเครื่องผู้ใช้)
  5. COMMIT — ยืนยันเฉพาะ transaction ย่อยของ Log (เพราะ AUTONOMOUS)
  6. EXCEPTION WHEN OTHERS — ถ้าพลาด: ROLLBACK เฉพาะของ Log แล้ว RAISE_APPLICATION_ERROR(-20001, ...) โยน error กลับให้ผู้เรียกเห็นข้อความไทยที่อ่านรู้เรื่อง
บทเรียนจาก deploy จริง 11/11: Procedure นี้เคยสถานะ INVALID บน server หลายวัน — เพราะมันอ้างตาราง Log และ Document_Detail ซึ่งถูกลบไปก่อนหน้านั้น Oracle ทำสิ่งนี้กับ procedure ทุกตัว: เมื่อตารางที่อ้างถูก DROP → procedure กลายเป็น INVALID ทันที เมื่อสร้างตารางกลับมาและ CREATE OR REPLACE ใหม่ → กลับมา VALID เช็คสถานะด้วย SELECT object_name, status FROM user_objects WHERE object_type='PROCEDURE';
จุดซักถาม: ทำไมใช้ MAX+SUBSTR ไม่ใช้ SEQUENCE? — เพื่อให้เลขต่อเนื่องไม่มีช่องว่าง (SEQUENCE กระโดดข้ามเลขเมื่อ rollback) แต่ยอมรับข้อจำกัด: 2 session บันทึกพร้อมกันอาจได้เลขซ้ำ → PK violation → ตัวใดตัวหนึ่ง rollback (การบันทึกพร้อมกันจริงควรใช้ SEQUENCE) ตอบแบบนี้แสดงว่าเข้าใจ trade-off
สคริปต์เต็ม 
CREATE OR REPLACE PROCEDURE SP_LOG_NOTIFICATION_SENT (
  p_log_type      IN VARCHAR2,
  p_message_sent    IN VARCHAR2,
  p_notification_message IN VARCHAR2,
  p_emp_code      IN VARCHAR2,
  p_detail_code     IN VARCHAR2,
  o_log_code      OUT VARCHAR2
) AS
  PRAGMA AUTONOMOUS_TRANSACTION;
  v_next_num NUMBER;
BEGIN
  -- 1. สร้างรหัส Log อัตโนมัติในรูปแบบ LOG-XXX
  SELECT NVL(MAX(TO_NUMBER(SUBSTR(code, 5))), 0) + 1
  INTO v_next_num
  FROM Log
  WHERE REGEXP_LIKE(code, '^LOG-[0-9]+$');

  o_log_code := 'LOG-' || LPAD(v_next_num, 3, '0');

  -- 2. บันทึกข้อมูลลงตาราง Log
  INSERT INTO Log (
    code,
    log_type,
    message_sent,
    notification_message,
    sent_datetime,
    emp_code,
    detail_code
  ) VALUES (
    o_log_code,
    p_log_type,
    p_message_sent,
    p_notification_message,
    SYSTIMESTAMP,
    p_emp_code,
    p_detail_code
  );

  COMMIT;
EXCEPTION
  WHEN OTHERS THEN
    ROLLBACK;
    RAISE_APPLICATION_ERROR(-20001, 'ข้อผิดพลาดในการบันทึก Log การแจ้งเตือน: ' || SQLERRM);
END SP_LOG_NOTIFICATION_SENT;

จุดประสงค์

พิสูจน์หน้างานว่า Transaction Processing ทำงานจริง ด้วยโครง 3 องก์: BEFORE (ก่อนเหตุ) → EVENT (เหตุการณ์) → AFTER (หลังเหตุ) ให้อาจารย์เห็นข้อมูลเปลี่ยนต่อหน้าเทียบก่อน-หลังได้

อธิบายการทำงานทีละองก์

  1. BEFORE — SELECT สถานะเอกสาร DD-004 → ต้องได้ "รอยืนยัน" (ค่าที่ seed ตั้งไว้ตั้งใจ)
  2. EVENT — 1 เหตุการณ์ 2 การกระทำ ใน anonymous block เดียว:
    • UPDATE Document_Detail SET status = 'อนุมัติแล้ว' WHERE code='DD-004' — การกระทำที่ 1: หัวหน้าอนุมัติ (transaction หลัก)
    • เรียก SP_LOG_NOTIFICATION_SENT(...) ด้วย named notation (=>) ส่งชื่อพารามิเตอร์ให้ชัด — การกระทำที่ 2: ระบบสร้าง Log อัตโนมัติ (transaction อิสระภายใน Procedure)
    • COMMIT — ยืนยัน transaction หลัก (UPDATE) ส่วน Log ถูก COMMIT ในตัวเองแล้ว
  3. AFTER — SELECT ซ้ำ 2 จุด: สถานะ DD-004 ต้องเปลี่ยนเป็น "อนุมัติแล้ว" และตาราง Log ต้องมีแถวใหม่ LOG-033 (32 จาก seed + 1 ที่เพิ่งเกิด)
จุดซักถาม: ถ้า UPDATE สำเร็จแต่ SP พัง จะเกิดอะไร? — UPDATE ยังไม่ถูก COMMIT (transaction หลักค้างอยู่) ผู้เรียกจะได้รับ RAISE_APPLICATION_ERROR และควร ROLLBACK ตัวเอง → สถานะเอกสารไม่เปลี่ยน แต่ Log ที่ SP พยายามบันทึกไม่เกิดเช่นกัน (เพราะ SP rollback ตัวเองก่อน) — คุยกันได้ทั้งสองแบบว่า design แบบไหนเหมาะกับธุรกิจไหน

จุดประสงค์

ครอบคลุมโจทย์ข้อ 4: "รายงานที่สำคัญที่ซับซ้อนมาก คือ รายงานในส่วนการประมวลผลกลุ่มงาน (ที่มีการใช้ Transaction tables / Master tables) ที่เกิดการ JOIN มากๆ" — รายงานนี้เชื่อมทั้ง 8 ตารางให้เห็นชีวิตเต็มวงจรของเอกสารในแถวเดียว: ใครร่าง → ใครอนุมัติ → ใครรับทราบ → ถูกแจ้งเตือนอะไรไปบ้าง

อธิบายการทำงานทีละ JOIN

JOINเชื่อมอะไรประเภทตาราง
Document ↔ Document_Detailเอกสารแม่ ↔ รายละเอียดย่อย (1:M)Master + Transaction
Admin + Department (adm)ธุรการผู้ร่าง + แผนกสังกัดMaster
Department_Head + Department (dh)หัวหน้าผู้อนุมัติ + แผนกสังกัดMaster
LEFT JOIN Receipt_Recordบันทึกการรับทราบ (อาจยังไม่มีใครรับ!)Transaction
LEFT JOIN Employee + Departmentพนักงานผู้กดรับ + แผนกMaster
LEFT JOIN Log (มีเงื่อนไข OR emp_code IS NULL)ประวัติแจ้งเตือนของรายละเอียดนั้นTransaction
  • ทำไม LEFT JOIN 3 จุดท้าย? — เอกสารบางรายการอาจยังไม่มีใครกดรับทราบ (ยังรออยู่) ถ้าใช้ INNER JOIN แถวเอกสารเหล่านั้นจะหล่นหายจากรายงานทั้งแถว ซึ่งผิดจุดประสงค์รายงานภาพรวม — เอกสารที่ยังไม่ถูกรับจะแสดง NULL ในคอลัมน์ receipt/receiver แทน
  • เงื่อนไข AND (lg.emp_code = emp.code OR lg.emp_code IS NULL) — กรอง Log ให้เข้าคู่กับพนักงานที่รับทราบจริง หรือแสดง Log ของแถวที่ยังไม่มีผู้รับ (เพราะ emp เป็น NULL การเทียบ = จะเทียบไม่ตรงเลย)
  • ORDER BY — เรียงเอกสาร → รายละเอียด → Log ล่าสุดอยู่บน ทำให้อ่านเรื่องราวย้อนเวลาได้ทีละเอกสาร

BA/Verify.txt

จุดประสงค์

โจทย์อาจารย์กำหนดให้ตรวจงานด้วย SQL แสดง Object ประเภท TABLE ที่ Database User เป็นเจ้าของ พร้อม Constraint ทั้งหมด — ไฟล์นี้คือ Script ของอาจารย์ที่แก้บั๊กให้รันได้จริง + query เสริมสำหรับตอบซักถาม

อธิบายการทำงานทีละ query

  1. Query หลัก (ของอาจารย์) — USER_TABLES LEFT JOIN USER_CONSTRAINTS เพราะตารางบางตารางอาจไม่มี constraint เลย ถ้าใช้ INNER JOIN ตารางนั้นจะหายไปจากรายงาน LEFT JOIN ทำให้ทุกตารางโผล่มาแม้ไม่มี constraint (คอลัมน์ฝั่ง constraint เป็น NULL)
  2. บั๊กที่แก้: ต้นฉบับอาจารย์ใช้ USER_TABLES.OWNER ซึ่งไม่มีคอลัมน์นี้อยู่จริง (ORA-00904) — เพราะ OWNER มีเฉพาะใน ALL_TABLES/DBA_TABLES ที่ต้องใช้สิทธิ์สูง → แก้เป็น USER AS OWNER (คำว่า USER คือ function คืนชื่อ user ปัจจุบัน)
  3. Query เสริม (USER_CONSTRAINTS + USER_CONS_COLUMNS) — แสดงว่า constraint แต่ละตัวผูกกับคอลัมน์ไหน ตำแหน่งไหน ใช้ตอบอาจารย์ว่า FK ตัวไหนชี้จากไหนไปไหน
  4. Query กรองเฉพาะงาน BA — เพราะ user นี้มีตาราง 2 โปรเจกต์ร่วมกัน 18 ตาราง ใช้ WHERE table_name IN (...) กรองดูเฉพาะของงานตัวเองเวลาอาจารย์ขอดูของงานเดียว
จำความหมาย CONSTRAINT_TYPE ให้ขึ้นใจ: P = Primary Key, R = Foreign Key (Referential), U = Unique, C = Check หรือ NOT NULL และชื่อ SYS_Cxxxxxx = ชื่อที่ Oracle ตั้งอัตโนมัติให้ constraint ที่เราไม่ได้ตั้งชื่อเอง (ส่วนใหญ่คือ NOT NULL)

-- ============================================================
-- Script ตรวจสอบผลการทำงาน: แสดง TABLE ที่ User เป็นเจ้าของ + Constraint
-- (ของอาจารย์ — เวอร์ชันแก้ไขให้รันได้จริง)
-- ============================================================
SELECT
    t.TABLE_NAME,
    t.TABLESPACE_NAME,
    USER AS OWNER,
    c.CONSTRAINT_NAME,
    c.CONSTRAINT_TYPE,
    c.TABLE_NAME
FROM USER_TABLES t
LEFT OUTER JOIN USER_CONSTRAINTS c
       ON (t.TABLE_NAME = c.TABLE_NAME)
ORDER BY t.TABLE_NAME, c.CONSTRAINT_TYPE, c.CONSTRAINT_NAME;

-- ============================================================
-- (เสริม) แสดงคอลัมน์ที่เกี่ยวข้องกับแต่ละ Constraint
-- ============================================================
SELECT
    c.TABLE_NAME,
    c.CONSTRAINT_NAME,
    c.CONSTRAINT_TYPE,
    cc.COLUMN_NAME,
    cc.POSITION
FROM USER_CONSTRAINTS c
LEFT JOIN USER_CONS_COLUMNS cc
       ON c.CONSTRAINT_NAME = cc.CONSTRAINT_NAME
      AND c.OWNER = cc.OWNER
ORDER BY c.TABLE_NAME, c.CONSTRAINT_TYPE, c.CONSTRAINT_NAME, cc.POSITION;

-- ============================================================
-- (เสริม) กรองเฉพาะตารางของโปรเจกต์นี้ (Document Approval)
-- ============================================================
SELECT
    t.TABLE_NAME,
    t.TABLESPACE_NAME,
    USER AS OWNER,
    c.CONSTRAINT_NAME,
    c.CONSTRAINT_TYPE,
    c.TABLE_NAME
FROM USER_TABLES t
LEFT OUTER JOIN USER_CONSTRAINTS c
       ON (t.TABLE_NAME = c.TABLE_NAME)
WHERE t.TABLE_NAME IN ('DEPARTMENT','DEPARTMENT_HEAD','ADMIN','EMPLOYEE',
